# Git 규칙

> 모든 팀원이 같은 방식으로 브랜치를 만들고, 커밋하고, PR을 올리기 위한 규칙입니다.
> 규칙을 바꾸고 싶다면 이 문서를 수정하는 PR을 올려 주세요.

## 한눈에 보기

```
이슈 만들기 → 브랜치 만들기 → 작업·커밋 → PR 올리기 → Squash merge → 브랜치 삭제
```

| 항목        | 규칙                                                  |
| ----------- | ----------------------------------------------------- |
| 브랜치 전략 | `main` + 작업 브랜치 (GitHub Flow)                    |
| 브랜치 이름 | `타입/#이슈번호-설명` → `feat/#12-map-route`          |
| 커밋 메시지 | `타입: 제목` → `feat: 지도 이동 경로 애니메이션 추가` |
| PR 제목     | 커밋 메시지와 같은 형식                               |
| 머지 방식   | Squash and merge                                      |

---

## 1. 브랜치

### 브랜치 전략

- `main`은 **항상 실행되는 상태**를 유지합니다. 배포도 `main` 기준입니다.
- 모든 작업은 `main`에서 새 브랜치를 만들어 진행합니다.
- `main`에 직접 push하지 않습니다. 반드시 PR을 거칩니다.
- 머지가 끝난 브랜치는 삭제합니다.

### 브랜치 이름

```
타입/#이슈번호-짧은-설명
```

- 설명은 **영어 소문자**와 `-`만 사용합니다.
- 이슈 번호를 꼭 넣습니다. 이슈 없이 작업하지 않습니다.

```
feat/#12-map-route
fix/#31-upload-heic-error
design/#18-passport-stamp
refactor/#40-trip-service
docs/#3-git-convention
```

### 타입 목록

브랜치 이름, 커밋 메시지, PR 제목에서 모두 같은 타입을 사용합니다.

| 타입       | 언제 쓰나요                                                 |
| ---------- | ----------------------------------------------------------- |
| `feat`     | 새 기능 추가                                                |
| `fix`      | 버그 수정                                                   |
| `design`   | CSS, 레이아웃 등 **화면 디자인** 변경                       |
| `refactor` | 동작은 그대로 두고 코드 구조만 개선                         |
| `style`    | 세미콜론, 들여쓰기 등 **코드 포맷만** 변경 (화면 변화 없음) |
| `docs`     | README, 문서 수정                                           |
| `test`     | 테스트 코드 추가·수정                                       |
| `chore`    | 패키지 설치, 설정 파일 변경 등 기타 작업                    |

> `style`과 `design`을 헷갈리기 쉽습니다. **화면이 바뀌면 `design`, 화면은 그대로이고 코드 모양만 바뀌면 `style`** 입니다.

---

## 2. 커밋

### 커밋 메시지 형식

```
타입: 제목

본문 (선택)
```

- 제목은 **한글로, 50자 이내**로 씁니다.
- 제목 끝에 마침표를 찍지 않습니다.
- 제목은 "~ 추가", "~ 수정"처럼 **명사형**으로 끝냅니다.
- 본문은 필요할 때만 씁니다. **무엇을 했는지보다 왜 했는지**를 적습니다.

```
feat: 지도 이동 경로 애니메이션 추가
fix: HEIC 사진 업로드 시 날짜를 못 읽는 문제 수정
design: 여권 도장 카드 간격 조정
refactor: 여행 통계 계산 로직을 utils로 분리
chore: zustand 설치
```

본문 예시:

```
fix: 아카이브에서 같은 날짜 여행이 한 번만 보이는 문제 수정

key로 날짜를 쓰고 있어서 같은 날짜의 여행이 겹쳐 보였음.
key를 여행 id로 변경.
```

### 커밋 단위

- 커밋 하나에는 **하나의 의도**만 담습니다. "지도 기능 추가 + 버튼 색 수정"은 커밋 두 개로 나눕니다.
- 작업 중간에도 자주 커밋해도 괜찮습니다. 머지할 때 Squash로 하나로 합쳐집니다.

---

## 3. PR (Pull Request)

### PR 규칙

- **PR 하나 = 이슈 하나**입니다.
- PR 제목은 커밋 메시지와 같은 형식으로 씁니다. Squash merge를 하면 **PR 제목이 그대로 `main`의 커밋 메시지**가 됩니다.

  ```
  feat: 지도 이동 경로 애니메이션 추가
  ```

- 본문에 `Closes #12`를 적어 두면, 머지될 때 이슈가 자동으로 닫힙니다.
- 변경은 **400줄 이내**를 권장합니다. 너무 크면 PR을 나눠 주세요. (목업 JSON, 이미지는 제외)
- 화면이 바뀌는 PR에는 **스크린샷**을 꼭 첨부합니다.
- 아직 작업 중이라면 **Draft PR**로 올립니다.

### 머지 조건

아래를 모두 만족해야 머지할 수 있습니다.

- [ ] CI(lint, 빌드) 통과
- [ ] `main`과 충돌 없음

조건을 만족하면 **PR을 올린 사람이 직접 Squash and merge** 하고, 브랜치를 삭제합니다.

## 4. 작업 흐름 예시

```bash
# 1. main을 최신 상태로
git switch main
git pull origin main

# 2. 이슈 #12용 브랜치 만들기
git switch -c feat/#12-map-route

# 3. 작업하고 커밋
git add .
git commit -m "feat: 지도 이동 경로 애니메이션 추가"

# 4. 작업 중 main이 바뀌었다면 내 브랜치에 반영
git pull origin main

# 5. push 후 GitHub에서 PR 만들기
git push origin feat/#12-map-route
```

### 충돌이 났을 때

- 충돌을 해결한 뒤에는 **직접 실행해서 동작을 확인**하고 push합니다.
- 다른 사람이 작성한 코드와 충돌했고 어떻게 고쳐야 할지 모르겠다면, 혼자 판단하지 말고 그 코드를 작성한 사람과 상의합니다.

---

## 5. 하지 말아야 할 것

- `main`에 직접 push
- `git push --force` (내 브랜치에서만, 꼭 필요할 때만 `--force-with-lease`로)
- `.env` 등 **비밀 값이 들어 있는 파일** 커밋
- `node_modules`, `dist` 커밋
- **용량이 큰 원본 사진** 커밋. 사진은 WebP로 변환하고 **1장당 500KB 이하**로 줄인 뒤 커밋합니다.
- 이슈 없이 작업 시작
